  RiskPilot 优化方向分析

  方向 1: 扩展规则字段 — 增加图结构派生特征

  问题: 当前规则只能用 node_degree 和 feature_dim_X 做阈值判断，无法表达"密集子图"、"欺诈团伙"等结构化模式。

  方案: 在 evaluator.py 中预计算更多派生特征，供规则使用：
  - clustering_coefficient: 节点聚类系数（邻居之间的连接密度）
  - k_core_number: k-core 值（衡量节点在多大密度的子图中）
  - triangle_count: 三角形数量（欺诈团伙常形成高三角网络）
  - neighbor_anomaly_ratio: 邻居中 GNN 判为异常的比例
  - pagerank: PageRank 值（识别网络中心节点）
  - community_id + community_anomaly_ratio: 社区检测 + 社区内异常率

  | 指标     | 预估值                                |
  |----------|---------------------------------------|
  | 预估提升 | Recall 27% → 50-60%, FPR 21% → 10-15% |
  | 难度     | 中等（网络算法计算 + prompt 更新）    |
  | 耗费     | ~2 天                                 |

  ---
  方向 2: GNN 嵌入驱动的规则 — 利用 Stage 1 输出

  问题: 当前规则完全忽略 GNN 嵌入向量，只用了原始特征和度数。

  方案:
  - 在 evaluator.py 中加载 node_embeddings.pt 和 gnn_predictions.pt
  - 增加规则字段: gnn_anomaly_score（GNN 输出的异常概率）, embedding_cluster_id（嵌入聚类后的簇ID）
  - 规则可以是: gnn_anomaly_score > 0.8 AND clustering_coefficient > 0.5
  - 这样规则实际上是对 GNN 判断的"可解释包装"

  | 指标     | 预估值                                          |
  |----------|-------------------------------------------------|
  | 预估提升 | Recall → 60-70%, FPR → 5-8% (直接继承 GNN 能力) |
  | 难度     | 中等                                            |
  | 耗费     | ~1.5 天                                         |

  ---
  方向 3: 规则模板升级 — 从单节点阈值到组合模式

  问题: 当前规则只判断"单个节点是否异常"，无法检测"一组节点构成欺诈团伙"。

  方案: 扩展 rule_parser.py 支持组合规则模板：
  - 子图模式: IF community_anomaly_ratio > 0.3 AND community_size > 5 THEN alert
  - 传播模式: IF node_anomaly AND neighbor_anomaly_count > 2 THEN alert
  - 时序模式: 预留接口，支持特征变化率条件
  - 需要修改规则 JSON schema，增加 rule_type: "single_node" | "subgraph" | "propagation"

  | 指标     | 预估值                                    |
  |----------|-------------------------------------------|
  | 预估提升 | Recall → 55-65%，尤其对团伙欺诈有显著改善 |
  | 难度     | 较高（需要社区检测算法 + 规则引擎重构）   |
  | 耗费     | ~3 天                                     |

  ---
  方向 4: LLM Prompt 优化 — 链式推理 + 少样本学习

  问题: 当前 LLM 直接生成规则，缺乏对数据分布的深度理解和失败案例的学习。

  方案:
  - Chain-of-Thought: 让 LLM 先分析每个异常模式的特征分布，再设计阈值
  - Few-shot: 将历史成功的规则（知识库中的）作为示例注入 prompt
  - 分布式阈值生成: 先让 LLM 分析"正常节点 vs 异常节点在各特征维度上的分布差异"，再据此设定阈值
  - 多轮对话: 不再一次性生成所有规则，而是逐模式生成 + 验证

  | 指标     | 预估值                            |
  |----------|-----------------------------------|
  | 预估提升 | Recall 提升 10-15%，FPR 降低 5-8% |
  | 难度     | 低（仅修改 prompt_templates.py）  |
  | 耗费     | ~1 天                             |

  ---
  方向 5: 闭环迭代策略优化 — 智能反馈

  问题: 当前优化迭代把整个评估报告丢给 LLM，LLM 经常"过度修正"导致更差（Recall 27% → 2%）。

  方案:
  - 定向反馈: 不给全部报告，只告诉 LLM "Recall 低，请放宽阈值"或"FPR 高，请收紧"
  - 贝叶斯优化: 对阈值做网格搜索/贝叶斯优化，不完全依赖 LLM 调参
  - A/B 测试: 每次迭代保留旧规则，新规则与旧规则比较取较优者
  - 阈值搜索: 在 LLM 生成的规则基础上，用贪心/网格搜索自动微调阈值

  | 指标     | 预估值                           |
  |----------|----------------------------------|
  | 预估提升 | 迭代稳定性大幅改善，避免规则退化 |
  | 难度     | 中等                             |
  | 耗费     | ~2 天                            |

  ---
  方向 6: 混合规则架构 — GNN 筛选 + LLM 精炼

  问题: 纯规则方式的天花板太低。

  方案:
  - 两阶段架构:
    a. GNN 先筛选 Top-K 高风险节点（已在 Stage 1 完成）
    b. LLM 规则只在 GNN 筛选结果上做精细分类（而非全量节点）
  - 这样规则不需要有很高的 Recall，因为 GNN 已经做了初筛
  - 规则专注于"区分不同风险类型"和"确定处置方式"
  - 评估方式改为: 规则在 Top-K 节点上的 Precision 和风险类型分类准确率

  | 指标     | 预估值                                             |
  |----------|----------------------------------------------------|
  | 预估提升 | Precision → 70%+ (在 GNN 候选集上)，实用性大幅提升 |
  | 难度     | 中等                                               |
  | 耗费     | ~2 天                                              |

  ---
  优先级排序

  | 优先级 | 方向                 | 理由                               |
  |--------|----------------------|------------------------------------|
  | P0     | 方向 4: Prompt 优化  | 投入最小，见效最快，1 天可完成     |
  | P0     | 方向 5: 闭环迭代优化 | 解决"越优化越差"的燃眉之急         |
  | P1     | 方向 2: GNN 嵌入驱动 | 直接利用已有 GNN 能力，性价比最高  |
  | P1     | 方向 1: 扩展派生特征 | 增加规则表达能力的基础设施         |
  | P2     | 方向 6: 混合架构     | 架构级改进，需前几个方向验证后再做 |
  | P2     | 方向 3: 组合规则模板 | 最复杂，依赖方向 1 的基础设施      |

  建议执行路径: 先做方向 4+5（1-2 天解决当前最紧急的问题），再做方向 2（快速提升指标），然后做方向 1+3（系统性地提升规则表达能力），最后做方向 6（架构升级）。


 优化计划：方向 4 (Prompt 优化) + 方向 5 (闭环迭代优化)

 问题总结

 1. Prompt 问题: LLM 直接生成规则，缺乏对数据分布的深度分析，导致阈值设定不合理（如 Recall 27%/FPR
 21%）
 2. 闭环迭代问题: LLM 收到完整评估报告后"过度修正"，优化后反而更差（Recall 27% → 2%）

 方向 4: Prompt 优化

 修改文件: src/stage2_llm/prompt_templates.py

 4a. SYSTEM_PROMPT 增强

 - 增加 Chain-of-Thought 指令：要求 LLM 先分析每个异常模式的特征分布差异，再设计阈值
 - 增加"思考过程"要求：输出规则前先输出分析步骤

 4b. RULE_GENERATION_PROMPT 重构

 - 在约束条件前增加"分析步骤"引导：
   a. 先分析正常节点 vs 异常节点在各维度的分布差异
   b. 找到能区分正常和异常的分界点
   c. 据此设定阈值
 - 改进示例规则：用 z-score 而非绝对值，更贴合实际分布

 4c. RULE_OPTIMIZATION_PROMPT 重构

 - 改为"定向反馈"：明确告诉 LLM 每条规则的具体问题和调整方向
 - 增加"增量调整"约束：阈值调整幅度不超过 20%，避免过度修正

 方向 5: 闭环迭代优化

 修改文件: src/stage2_llm/rule_generator.py, src/pipeline.py

 5a. 定向反馈 (rule_generator.py - optimize())

 - 不再传整个 report，而是为每条规则生成针对性反馈：
   - Recall 低 → "请降低阈值 X% 以提高召回"
   - FPR 高 → "请提高阈值 X% 以降低误杀"
   - Precision 低 → "请增加 AND 条件以提高精度"

 5b. 阈值微调策略 (rule_generator.py - 新方法 _threshold_search)

 - 对 LLM 生成的规则做贪心搜索：自动微调每个条件阈值
 - 遍历每个条件的 value，在 ±30% 范围内搜索最优值
 - 选择 F1 最高的阈值组合
 - 这层搜索在 LLM 生成规则后、沙盒评估前执行

 5c. 迭代稳定性 (pipeline.py)

 - 增加"历史最优"追踪：记录每轮最好的规则集
 - 如果优化后整体变差，回退到上一轮的规则
 - 增加 early stop：连续 2 轮无改善则停止
